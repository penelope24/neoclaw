# Agent 架构讨论备忘录

## 我们的实现 vs 成熟 Agent 系统

### 1. Tool Call 机制

**我们的方式**：LLM 在普通文本中输出 JSON，我们用正则解析：
```
{"tool": "youtube_summary", "args": {"url": "..."}}
```
缺点：格式稍有偏差就解析失败，依赖 prompt 诱导模型输出正确格式。

**现代 API（Claude / OpenAI）**：Tool call 是协议层的一等公民，有独立消息类型，模型经过专门训练，结构化且可靠。

---

### 2. 推理过程是否显式

| 方式 | 特点 |
|------|------|
| 我们的实现 | 隐式，LLM 一步决定调不调用工具，推理不可见 |
| ReAct 框架 | 显式 Thought → Action → Observation 循环，推理可观测 |
| Claude Code 等 | 独立 Planning 阶段，先制定计划再执行，可中途修订 |

---

### 3. 上下文管理

**我们的方式**：`history` 列表无限增长，直到撑爆 context window。

**成熟系统**：滑动窗口、历史摘要压缩、分层记忆（短期 / 长期 / 向量检索）、工具结果的选择性保留。

---

### 4. 并行与编排

**我们的方式**：完全串行，一次调用一个工具。

**成熟系统**：单次回复可发出多个 tool call 并行执行，可生成子 Agent 处理独立子任务。

---

### 5. 本质差异

> 我们的 Agent 是**被动响应式**的——LLM 说什么就做什么，一步一步走。
> 成熟的 Agent 系统是**主动规划式**的——先理解任务全貌，制定计划，并行执行，失败时自动调整策略。

`youtube_summary` 里手动实现的 map-reduce，本质上是在弥补"缺乏主动规划"的不足。成熟系统中这类多步骤任务可以由 Agent 自己分解编排。

---

## Tool Calling 协议是否统一？

**不统一。** 各家格式不同：

| 提供方 | 格式特点 |
|--------|----------|
| OpenAI | `tool_calls` 数组，含 `function.name` + `function.arguments` |
| Anthropic | `tool_use` block，含 `name` + `input` |
| Ollama | 模仿 OpenAI，但细节有差异 |
| 我们 | 自定义 `{"tool": ..., "args": ...}` |

**工程上的解决方式**：在框架层做协议适配（LangChain、LlamaIndex 的思路），统一抽象 `Tool` 接口，底层为每个模型写适配器。

**更深的问题**：协议格式只是表面，真正的差异是模型的 tool call **能力**本身——同样的协议，GPT-4o 能稳定处理嵌套参数，7B 本地模型可能输出格式错误。适配层可以统一格式，统一不了能力。

## Planning 模式 vs 硬编码逻辑

### 核心张力："自主性 vs 确定性"

```
硬编码逻辑          混合          纯 Planning
───────────────────────────────────────────────
确定、快、可调试     ←→        灵活、但慢且不可控
```

### Planning 模式的真实成本

- CoT 过程消耗大量 token，延迟高
- 推理路径不可预测，同样输入可能走不同分支
- 出错时难以调试——不知道模型在哪一步"想错了"

### 成熟系统实际上大量依赖硬编码

Claude Code 里很多行为是写死的（读文件前必须先 Glob、破坏性操作要确认等），不是模型自己 planning 出来的。模型的自主决策空间被限制在"选哪个工具、参数是什么"，而不是"要不要走这条流程"。

### 实用分层原则

| 任务类型 | 适合的方式 |
|----------|-----------|
| 固定流程（如三步总结） | 硬编码，快且可靠 |
| 有限选择（如选用哪个工具） | LLM 决策，成本低 |
| 开放性复杂任务 | Planning，接受高成本 |

> **Planning 是能力的兜底，不是首选。**
> 能明确编码的逻辑就明确编码，planning 留给真正需要灵活应对的场景。

我们的 `youtube_summary` 三步流程完全硬编码，正是这一原则的体现——稳定、可预期、执行快。
